# Cron timezone contract

Status: implemented and locally verified on 2026-09-21. This document describes
the Core RPC and persistence contract. It does not certify a deployed relay,
notification delivery, or mobile release.

## Client contract

For every recurring schedule created or edited by a user-facing client, send the
user's current IANA timezone in the existing `schedule.tz` field:

```json
{
  "kind": "cron",
  "expr": "0 9 * * *",
  "tz": "Europe/Madrid"
}
```

Core accepts this shape through `cron.add` and through
`cron.update.params.updates.schedule`. `cron.list`, `cron.add`, and `cron.update`
return the same value at `job.schedule.tz`. Core stores it as `schedule.tz` in
`cron/jobs.json`, so it survives agent restart. A client should preserve the
stored timezone when editing unrelated fields.

IANA identifiers such as `Europe/Madrid`, `America/New_York`, and `UTC` are
accepted. An explicit unresolvable identifier is rejected with the existing RPC
`INVALID` error and does not mutate the job. Offset abbreviations such as `EST`
do not express complete daylight-saving rules and should not be generated by a
client.

If a legacy job already contains an invalid explicit timezone, startup preserves
the record and timezone text but pauses the job instead of continuing the older
silent UTC fallback. Updating it with a valid schedule makes it runnable again.

## Evaluation rules

- A cron expression with `tz` is evaluated as wall-clock calendar time in that
  zone, independently of the execution host timezone.
- A cron expression without `tz` uses the execution host's timezone. This is a
  compatibility fallback for persisted legacy records and CLI callers.
- A nonexistent wall time in a spring-forward gap is skipped.
- An ambiguous wall time in a fall-back fold runs once, at the earlier
  occurrence. It does not run again in the repeated hour.
- `atMs` remains an absolute Unix timestamp in milliseconds.
- `everyMs` remains an elapsed duration and is not shifted by timezone changes.

The next run is persisted as an epoch millisecond value, then recomputed from the
expression and stored timezone when the service starts. A timezone database
update can therefore affect future calculations without rewriting the schedule.

## Read metadata

`cron.list` also returns `schedulerTimeZone` with `id`, `name`, and
`utcOffsetSeconds`. This describes the agent host clock for diagnostics and for
labeling legacy schedules whose `schedule.tz` is absent. `id` can be null on a
platform that does not expose an IANA identifier. It must not replace a job's
explicit `schedule.tz`, and a current UTC offset must not be treated as a DST
rule.

## Compatibility boundary

No relay or Firestore registration shape changes are required. Timezone is part
of the Core schedule RPC and local job record. Clients that omit `tz` remain
accepted, but their recurring schedules follow the agent host rather than the
user's device after future recomputations.

Core declares `python-dateutil` directly for host-zone discovery and `tzdata`
directly for the IANA database. The Nuitka entry includes the `tzdata` package
and resource files so a standalone Windows agent does not depend on an OS IANA
database. Local checks cover the dependency lock and build directives; native
Windows artifact smoke testing remains part of the external build workflow.
